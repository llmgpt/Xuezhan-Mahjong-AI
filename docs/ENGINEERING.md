# 开发与反馈回路

借鉴 OpenAI 的 [Harness engineering 实践](https://openai.com/index/harness-engineering/)：让仓库里的目标、边界、测试结果和失败原因可被人和开发代理直接检查。`AGENTS.md` 只做入口，详细决定放在对应文档中；不为当前不存在的功能建立大套空目录。

## 文档职责

- [README.md](../README.md)：给访问仓库的人看目标与当前状态。
- [docs/PROJECT_PLAN.md](PROJECT_PLAN.md)：产品里程碑、规则待定项和建议的评价方法。
- [ARCHITECTURE.md](../ARCHITECTURE.md)：阶段性技术选择、模块依赖和信息边界。
- 本文：开发过程与验证方式。

每个决定只在一个主要位置维护，其他文档使用链接。代码出现后，如实际实现与文档不同，应在同一次改动中更新文档。

## 从需求到可验证结果

1. 写清一个小范围的可观察结果，例如“给定手牌和缺门时，合法出牌集合符合规则表”，并准备固定牌例。
2. 对规则、计分、流程或建议算法先运行失败测试，再完成实现；界面任务则检查实际操作路径和提示文字。
3. 运行与改动相关的检查，复现并修复失败。随机对局保留种子，方便重放。
4. 核对页面行为、建议的信息范围与文档，提交聚焦改动。

首个代码脚手架建立时，由 Codex 一并生成并验证包管理锁文件、格式化、静态检查、测试、构建和 CI。CI 至少覆盖类型检查、格式与静态检查、规则测试和生产构建；有可玩页面后加入关键流程的浏览器检查。实际命令写入 README 或 AGENTS.md，避免只存在于聊天记录中。

当前仓库只有文档，以上是实施标准，不表示脚手架或 CI 已建成。

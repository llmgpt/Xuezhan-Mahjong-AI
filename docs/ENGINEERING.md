# 开发与反馈回路

借鉴 OpenAI 的 [Harness engineering 实践](https://openai.com/index/harness-engineering/)：把目标、边界、验证方式与防退化规则固化到仓库和自动化检查中，不依赖代理“自觉记住”。

## 文档职责与生命周期

| ---------------------------------------- | ---------------------------------------------------------- | ------------------------------------ |
| [AGENTS.md](../AGENTS.md)                | 代理总入口与核心约束                                       | 仅放导航与硬规则                     |

## 防止再次失控的机制

1. **取代即清理，禁止只增不删**：新规则或新结论生效时，同步改写或归档旧表述；历史演进留在 `git log`，不堆在交接文档里。
2. **自主运行（如 `/goal`）先定停止条件**：开始前明确“够好即停”的可验证标准和轮次/范围上限，避免无止境刷分导致代码与文档膨胀。
3. **未追踪目录不作长期证据**：`local/` 只放临时草稿、截图和一次性脚本；核心文档与研究索引不引用 `local/` 下的具体文件或目录作为证明。
4. **视觉与交互改动须目视确认**：单元测试证明结构与文案，不证明人眼“认得出、好用”；牌面、排版、弹窗改动须对照参考图或真实页面截图确认后再合并。

## 从需求到可验证结果

1. 写清小范围可观察目标，规则、计分、流程或建议算法改动先运行失败测试再实现；界面/视觉改动先对齐参考或操作路径。
2. 每次提交前运行 `npm run check`，一次性检查：Prettier 格式、ESLint、TypeScript 类型、`npm run check:docs`（文档行数、目录位置、状态登记、无 `local/` 依赖与相对链接有效性）、Vitest 单元测试和 `vite build` 生产构建。
3. 核对差异和敏感信息，确认无误后在主题分支聚焦提交。CI 同步运行 `npm run check` 与 Python 外部策略检查（`.github/workflows/check.yml`）。
